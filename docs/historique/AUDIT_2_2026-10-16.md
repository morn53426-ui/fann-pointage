# Deuxième audit — 16 octobre 2026

Périmètre : authentification/sessions, serveur HTTP, accès SQL, pointage au poste partagé, Docker/compose/CI, dépendances.
Méthode : lecture du code, recherche d'interpolations SQL, `npm audit`, tests (dont contrôle négatif : le nouveau test échoue sur l'ancien code).

## Défaut corrigé
| Gravité | Constat | Correctif |
|---|---|---|
| **Élevée** (mode PostgreSQL) | **Pointage au poste partagé : le départ était refusé** (« L'arrivée doit être enregistrée avant le départ ») dès que l'arrivée datait de plus de 2 minutes. Cause : la requête `pointsRecents` (`operations-postgres.ts`) ne lisait que les pointages des 2 dernières minutes pour savoir si l'arrivée existait. Conséquence inverse : une seconde arrivée tardive était acceptée (doublon). Le pointage individuel (`postgres.ts`, par `poste_code`) était correct ; seul le poste partagé était touché. | La requête lit aussi tous les pointages du **même planning** (`planning_id`). 2 tests de régression ajoutés (départ 8 h après l'arrivée accepté ; seconde arrivée refusée). Ils échouent sur l'ancien code et passent sur le nouveau. |

## Constats non corrigés (à décider)
| Gravité | Constat | Recommandation |
|---|---|---|
| Moyenne | **Limite de connexion par IP : 30 échecs / 15 min.** Derrière une même passerelle (NAT d'hôpital, ou Docker sans `TRUST_PROXY=1`), tous les postes partagent la même IP : une seule personne qui se trompe ou qui attaque peut bloquer la connexion de tout le monde pendant 15 min. | Garder `TRUST_PROXY=1` derrière Caddy (déjà prévu dans `compose.https.yaml`) ; prévoir un déblocage administrateur ; persister le limiteur (déjà noté au premier audit). |
| Faible | **Déconnexion = côté navigateur seulement.** Le jeton reste valide 8 h côté serveur ; seul « révoquer les sessions »/changement de mot de passe l'invalide. | Appeler la révocation (`session_version + 1`) à la déconnexion, ou réduire la durée. |
| Faible | Rejeu d'un pointage station (`idempotencyKey`) : la recherche du rejeu précède la vérification du jeton du badge. Il faut connaître l'UUID de l'agent **et** la clé d'idempotence (aléatoire) ; la fuite se limite à l'identifiant/horodatage du pointage, réservée aux comptes responsable/admin. | Vérifier le badge avant de répondre au rejeu, ou accepter le risque (réponse hors-ligne). |
| Info | Politiques RLS du rôle `fann_app` : `USING (true)` sur les tables métier. Les droits ne reposent donc que sur le code applicatif (vérifié rôle par rôle dans les routes), sans défense en profondeur au niveau base. | Acceptable pour ce modèle ; à documenter. |
| Info | Le badge QR est un secret **permanent** jusqu'à révocation (par conception : hors ligne, imprimé). Un badge photographié permet de pointer à un poste partagé tenu par un responsable. | Procédure de perte/renouvellement (existe) ; former les responsables. |
| Info | CI : pas de `npm audit` ni de tests sur une vraie base PostgreSQL ; image Docker non épinglée par digest ; `--experimental-strip-types` en production (déjà noté). | Ajouter `npm audit --omit=dev` et `npm run test:postgres` à la CI. |

## Points vérifiés sans anomalie
- **Injection SQL** : toutes les requêtes sont paramétrées ; les seules interpolations dans le SQL sont des fragments fixes choisis par le code (périmètre, liste de conditions numérotées).
- **Sessions** : HMAC-SHA256, comparaison en temps constant, expiration, version de session ; l'inconnu déclenche un calcul scrypt factice (pas d'énumération par le temps de réponse). Clé de badge dérivée, distincte.
- **Serveur HTTP** : traversée de répertoire bloquée (normalisation + préfixe), corps limité à 32 Ko (128 Ko pour les photos), erreurs sans détail technique, `/healthz` `/readyz` sans fuite, CSP stricte (`script-src 'self'`, `frame-ancestors 'none'`, pas de style en ligne), aucun `innerHTML`/`eval`.
- **Conteneur** : utilisateur non root, système de fichiers en lecture seule, `cap_drop: ALL`, `no-new-privileges`, limites mémoire/processus, base liée à `127.0.0.1`, `.env` exclu de l'image et du dépôt.
- **Dépendances** : `npm audit --omit=dev` → 0 vulnérabilité (1 seule dépendance de production : `pg`).

## Vérifications
`tsc --noEmit` sans erreur ; `npm test` : 300/300.

## Non vérifié
Aucune exécution sur une vraie base PostgreSQL : le test de régression émule la base avec un client simulé (il prouve la logique de la requête, pas son exécution SQL réelle). Lancer `npm run test:postgres` et une recette de bout en bout (arrivée puis départ au poste partagé) avant la production.
